# 验收条件与证据管理

## 最小验收依赖矩阵

需要浏览器验收时，在理解需求阶段建立下表，复用现有任务记录即可，不额外要求用户填写或新增交付文件。先从需求、代码及已登录页面可得信息填入；正式触发前更新实际条件。仅纳入本次范围，简单单路径可以合并为一行。

| 业务路径与目标事件 | 账号/策略条件 | 环境与设备 | 必需动作及副作用 | 已有授权范围 | 当前缺口与补验条件 |
|---|---|---|---|---|---|
| 按具体入口区分展示、点击、成功 | 资格、分组或订阅状态；不记账号标识 | 本次实际要求 | 如点击即创建订单，支付消耗资格 | 指向用户已确认的动作和金额等边界 | 已满足、待核实或缺失；写明恢复条件 |

同一容器中的不同商品或入口分别关联目标事件，例如订阅套餐和抽屉首充不能相互替代。矩阵暴露条件依赖，不扩大测试范围；缺条件仅阻断依赖场景，其他已具备条件的工作继续。

已有明确授权跨轮次复用，不因重读 skill、重新登录检查或重新生成报告再次询问。创建订单与付款分别记录；只有动作、金额、目标或风险超出已有授权，或适用工具规则要求时才确认。发现缺口时提前说明，具体副作用仍在动作前核对授权；不得把“验收全部埋点”当作所有购买操作的授权。

## 先安排业务顺序

正式触发前，从业务代码、需求和当前页面确认本次场景的资格、分组、余额等必要条件。仅记录条件描述，不保存账号 ID、联系方式或凭证。按场景列出：前置条件、执行后状态变化、是否消耗其他场景所需条件、恢复方式和当前是否满足。

先执行依赖某条件的场景，再执行使条件失效的动作。提交订单、付款、领取、关闭或删除等动作若会影响剩余覆盖项，在动作前再次检查剩余场景；不能只凭已获得动作授权跳过该检查。没有依赖关系时不强制固定顺序。

例如首充验收：有资格且符合自动弹出分组的账号，先验证生成完成弹出；有资格且余额不足的账号，先验证积分不足入口；再覆盖手动入口、关闭和重开；最后支付。生成可能消耗积分，支付会消耗首充资格，应结合余额与分组安排，必要时使用不同测试账号。已无法满足的条件要准确标记，不声称曾验证，也不通过强改分组、直接调用埋点或伪造资格来代替业务操作。账号重置需要另行明确授权。

## 查询预检

在正式页面触发前运行一次：

```bash
node scripts/verify-sensors-events.mjs --preflight --spec contract.json --environment local --format json
```

复用正常只读凭证解析、环境绑定与查询路径，取一个事件、最多一条结果，确认网络、认证及查询权限。零条结果也可通过。输出 `kind=query-preflight`，没有验收 `results`，不得作为入库证据；不触发浏览器、不替代正式等待。失败先定位网络或权限，恢复后再预检；避免先消耗业务资格才发现无法查询。

## 逐步追加证据

先准备并校验完整 Journey，再使用新鲜页面证据执行。每一步后可调用：

```bash
node scripts/append-browser-evidence.mjs --session <会话目录> --input step-evidence.json
```

输入为 `{ "step": <真实步骤记录>, "results": [<本步已取得的事件证据>] }`；可选传 `triggerWindow`（明确提供已观测的时间范围）和 `accountConditions`（非敏感条件描述数组）。已有结果不要重复添加。该命令仅支持工具自有会话，校验旅程和已完成前缀后原子写入；不会生成时间、匹配数或通过状态。字段或断言有误时保留原文件不变。全部完成后仍须运行完整 `validate-browser-report.mjs`；前缀校验通过不代表完整验收通过。

步骤和事件结果可以带 `reason`：

```json
{
  "code": "PRECONDITION_UNMET",
  "message": "本轮付款后首充资格失效，剩余入口未执行",
  "recovery": "使用仍有首充资格且符合该入口条件的测试账号",
  "changedByRun": true
}
```

原因 code 为 `NOT_EXECUTED`、`PRECONDITION_UNMET`、`QUERY_FAILURE` 或 `VALIDATION_FAILURE`。沿用原状态码：未执行为 `NOT_RUN`（步骤未执行可记 BLOCKED），条件缺失为 `BLOCKED`，查询失败为 `QUERY_FAILED`，验证失败为 `FAILED` 或具体契约错误。`changedByRun` 必须真实记录。完整 runner 只接受已成功执行的旅程；未执行场景用独立阶段报告交给汇总器，不伪造浏览器成功证据。

`accountConditions` 记录本轮真实覆盖的条件，如“仍有首充资格；前端 B 组”，不推断其他分组。SDK 不能捕获为 `NOT_AVAILABLE`，不能写成未发送；报告显示“未直接捕获”，其是否为必需门禁由契约决定。

## 跨事件关联

Version 2 契约可选增加 `crossEventAssertions`，旧契约不受影响。只在需求要求一致性时使用，不把参考示例变成约束：

```json
{
  "crossEventAssertions": [{
    "id": "purchase-attribution",
    "eventIds": ["popup-show", "purchase-click", "purchase-success"],
    "groupBy": "exposure_id",
    "equalProperties": ["offer_entry", "country_tier", "price_group", "timing_group", "product_id", "price_id"],
    "counts": {
      "popup-show": { "min": 1, "max": 1 },
      "purchase-click": { "min": 1, "max": 1 },
      "purchase-success": { "min": 1, "max": 1 }
    }
  }]
}
```

`eventIds` 必须是本次环境中 required 神策事件；`groupBy` 是真实上报的稳定关联字段。按事件 match 选择候选后分组，检查每组参与事件及字段的类型和值一致性。`counts` 为可选且须有需求依据，适用于每个关联组；未声明时多条同类记录视为关联歧义，不自动宣称重复上报。缺键、字段漂移、缺事件、同一记录命中多个事件、不同环境或窗口、查询失败和截断都不能通过。默认环境 URL 字段为 lmweb_url，在线查询使用配置字段。输出只含断言结果和原因，不新增原始关联标识副本。

重新打开等需要不同关联键的场景，应分段记录实际打开过程，并检查每组的次数约束；没有需求声明的次数上限时，不用关联断言代替曝光唯一性证明。

## 失败恢复与清理

校验失败时保留原始 bundle、自有会话标识和诊断，不执行收缩清理。原 bundle 是私有恢复材料；未知字段可能含敏感内容，不复制到诊断或最终报告。JSON 无法解析时同样保留原字节。修正输入后：

```bash
node scripts/run-browser-ingestion-verification.mjs --resume --session <会话目录>
```

已通过输入校验的查询失败会话，恢复时契约、旅程和浏览器报告必须完全一致，继续使用原触发窗口，不再操作页面；有业务修复或新动作应建立新会话。恢复不自动无限重试，每次仍遵守原有最多两轮查询政策；只有发现并解除故障才显式恢复。历次运行写入 `previousRuns`，成功入库证据保留 `recoveryHistory`，不将失败伪装成从未发生。

多轮独立报告可通过重复 `--browser` / `--ingestion` 等参数汇总。同一场景状态冲突会保留失败或标为需确认，不用最后一份通过覆盖旧失败。查询故障应使用上述显式恢复；业务修复后以新轮结果交付，并保留旧轮报告作历史说明，不把互相矛盾的轮次冒充同一轮证据。统计单位是“事件 × 平台 × 环境”的验收场景，不能解释为全部用户分组覆盖率。

成功后确认最终报告已经写入且可读取，再运行 `--cleanup --session`。失败输入应先恢复或完成诊断交付再按需要清理；本工具只清理自己的会话。
